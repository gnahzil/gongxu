# 未知项发现（Unknowns Pass）

**触发场景：** brainstorming 探索后、planner 拆执行单元前，以及 executor / evaluator
发现状态与代码或环境不一致时。

## 1. 核心定义

任务描述、prompt、skills、context 是「地图」；代码库、业务事实、运行环境和组织约束是「领土」。两者之间的差距就是未知项。强模型失败时，很多时候不是能力不够，而是未知项没有被提前发现、记录和冻结。

## 2. 四类未知项

| 类型 | 含义 | 典型处理 |
|------|------|----------|
| 已知事实 | 用户已明确说出、代码已证明的内容 | 不可重建结论写入 state；可重查事实只存 Source Pointer |
| 已知缺口 | 已意识到但还没决定的内容 | 只问会改变架构、接口、数据或验收的问题 |
| 隐性标准 | 用户难以文字描述，但看到方案或原型能判断 | 用参考实现、样例、原型或 2-3 个方案逼出偏好 |
| 未知盲区 | 用户和 agent 一开始都没意识到的风险 | 扫代码、文档、历史实现和约束，做 blindspot pass |

## 3. 执行步骤

1. **先扫领土**：读当前仓库结构、相关 `AGENTS.md` / `WORKSPACE.md`、长期领域文档、历史实现和最近 diff，再列未知项。
2. **只保留会改变结果的未知项**：影响架构、接口、字段、数据、权限、验收或发布的才进入清单。
3. **按爆炸半径排序**：先处理会影响 public contract、DDL、跨服务契约、人工用例的未知项。
4. **每次只问一个关键问题**：使用 `grilling`，问题必须说明回答会改变什么设计选择并给出推荐答案。
5. **冻结或转交**：主 agent 把结论合并到 `state.md`；阻塞实现的留在
   `Open Questions`，其余低风险事实通过来源指针按需重查。

## 4. 产物要求

- `Frozen Contract` 保存已确认且后续不可重新推导的结论。
- `Decisions` 保存非显然选择及必要理由。
- `Open Questions` 保存未冻结 blocker；存在时状态不得进入 `approved`。
- executor / evaluator 在结构化返回中报告新增未知项，由主 agent 合并。

## 5. 硬门槛

- 影响 public contract、DDL、跨服务消息、权限、安全、人工端到端用例的未知项，未冻结前不得进入业务实现。
- 规范领域术语、需求锚点与代码现实互相矛盾且会改变业务边界时，按 blocker 处理，禁止静默覆盖。
- 不把普通 TODO、低影响文案、机械重命名写成未知项。
- 不因为发现未知项就扩大 scope；优先通过澄清、参考实现或保守默认消除它。

## 6. 自检 checklist

- [ ] 是否列出了至少一轮 blindspot pass 结果，或明确说明本任务无 blocker 级未知项？
- [ ] 每个 blocker 级未知项是否已冻结？无法冻结的项是否由用户移出本期范围并重新标为非阻塞项，而不是直接转实施风险？
- [ ] `state.md` 是否能用稳定 ID 串起契约、执行单元和验收？
- [ ] 是否避免把无关优化包装成 unknowns 引入本期？
