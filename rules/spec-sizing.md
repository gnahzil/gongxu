# 需求规模与子 Spec 拆分

## 1. 两个正交维度

先判断迷雾，再在路线清晰时判断规模：

- **迷雾**回答“能否在一次会话内可靠说清关键路线”；
- **规模**回答“包含几个可独立验收、上线或回滚的业务结果”。

服务数量和 PRD 长度都不能代替这两个判断。跨服务但业务结果不可分割时仍是单
Spec；文档很长但路线清晰时也不进入 Wayfinder。

| 迷雾 | 规模信号 | 流程 |
|---|---|---|
| 路线清晰 | 极小 | 确认后直接修改和验证 |
| 路线清晰 | 一个独立业务结果 | 单 Spec 完整 brainstorming |
| 路线清晰 | 多个独立业务结果 | 直接拆分并确认多个子 Spec |
| 高迷雾 | 暂不可可靠判断 | 进入 Wayfinder，收敛后重新判定规模 |

只有目标可以命名、但关键决策无法在一次会话内澄清并阻碍可靠规模判定时，才算
高迷雾。目标尚不能命名时先用 `grilling` 澄清目标；路线清晰的单 Spec 或大需求
都跳过 Wayfinder。

## 2. 三档规模判定

| 档位 | 判定 | 流程 |
|---|---|---|
| 极小 | 机械局部改动，影响面自明，不碰硬门槛 | 确认后直接修改和验证 |
| 单 Spec | 一个独立业务结果可在一个新 agent 上下文内规划和交付 | 单个 `state.md` |
| 大需求 | 包含多个可独立验收、上线或回滚的业务结果 | `index.md` 加多个子 Spec |

规模判定必须发生在路线清晰之后。Wayfinder 的 Decision 只消除决策迷雾，不是
子 Spec、实现任务或 Execution Unit。

## 3. 极小档

以下条件必须全部满足：

- 一句话能说清行为和目标文件；
- 不引入逻辑分支、公共接口或数据结构；
- 无跨文件调用链影响；
- 不涉及 DDL、跨服务、第三方、PRD/视觉来源 或公共 API。

流程：说明改动与文件 → 用户确认 → 修改 → 非测试验证 → 报告 diff。任何条件
失效就进入 brainstorming。

## 4. 单 Spec 与大需求

用“能否由一个子 Spec 独立验收”判断，而不是计算步骤数量。出现下列任一信号
时倾向拆分：

- 两个以上可独立上线或回滚的业务结果；
- 不同结果具有各自的用户、验收入口或生命周期；
- 存在明确串行阶段，后阶段可以作为独立交付；
- 多个结果互不依赖，可以并行推进。

拆分只做浅层结构发现。产出路径：

```text
docs/gongxu/initiatives/YYYY-MM-DD-<initiative>/index.md
```

索引按 `rules/ai-first-artifacts.md` 编写。用户确认拆分后，父流程只维护索引；
每个子 Spec 都必须从 brainstorming 起点完整执行状态建立、领土探索、Unknowns
Pass、精确需求锚点、grilling、方向确认和状态冻结，开始时惰性创建自己的
`state.md`。父级 Destination、来源和 Shared Contracts 只能作为输入，不能替代
子 Spec 探索。父需求不得冻结 视觉来源 Coverage，子 Spec 不得复用父级模糊范围。

Wayfinder 收敛后必须回到本节重新判定：一个业务结果进入一个子 Spec；多个结果
先更新 `index.md` 的 Sub Specs 并等待用户确认。不得把 Decision 直接转换成子
Spec 或实现计划。

## 5. 自检

- [ ] 已先判断迷雾，且没有把“大 PRD”误判为高迷雾。
- [ ] 路线清晰的单 Spec 或大需求已跳过 Wayfinder。
- [ ] Wayfinder 收敛后已重新判定规模，没有沿用旧猜测。
- [ ] 极小档四项条件全部满足，否则已升档。
- [ ] 每个子 Spec 都有独立业务结果和验收边界。
- [ ] 每个子 Spec 都从 brainstorming 起点完整重跑。
- [ ] 跨服务逻辑一体没有被机械拆散。
- [ ] 父索引只保存地图，没有复制子 Spec 设计细节。
- [ ] 视觉来源 精确取证只发生在当前子 Spec。
